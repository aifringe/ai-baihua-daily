# 网站质量审计报告（2026-09-28）

审计对象：`https://news.czrshe.com/` 与当前 `main` 工作区
审计方式：线上实际操作、7 个视口测量、代码与配置审阅、构建与测试、135 个原文链接状态检查。
限制：未取得真实用户 75 分位 Core Web Vitals 数据；第三方链接的 403/429 可能含机器人防护，需要人工浏览器复核。
本报告只记录问题，没有修改产品代码、内容、样式或服务器配置。

- P0：0 项。
- P1：5 项。

- 浏览器检查未出现控制台错误；云端 AI 能基于当前新闻回答。

## P1 重要

| 问题 | 出现位置与证据 | 影响 | 建议修改 |
| --- | --- | --- | --- |
| 文字对比度和触控目标不达标 | 390px 自动测量发现分类标签对比度约 2.87:1，来源文字约 2.99–4.38:1；新闻摘要约 4.28:1。多个文字链接可点击高度仅 15–18px，手机排序框渲染高度约 17px | 弱视、低亮度环境和手指操作用户难以阅读或点击，违反 WCAG 2.2 AA 的相关要求 | 提高灰色/橙色文字对比度；扩大“读白话解读”“查看原文”、排序框等实际点击区域至至少 24px，建议 44px |
| 新闻仍存在明显语义重复 | 精确 ID、URL、标题重复均为 0，但相似标题检查发现至少四组同一事件：Gemini 入侵三家公司出现 4 个版本；Claude 入侵 OpenAI 出现多个版本；Gemini 3.8 数字人出现两个版本；Meta Muse Charm 出现两个版本 | 重复新闻占用列表，削弱“精选”和去重承诺，可能让用户误以为是不同事件 | 在更新脚本中增加事件实体、时间、公司和行为的语义聚类；合并后保留多个来源和更正关系 |
| AI 接口信任浏览器提交的新闻正文 | `public/api/chat.php` 接收客户端完整 `article` 并直接拼入 system prompt；`articleId` 未用于服务端读取或核对可信新闻 | 任何调用者都可提交任意正文，让公共接口变成通用模型代理，增加提示注入、费用滥用和错误归因风险 | 服务端仅接受 `articleId` 与对话；从服务器 `news.json`/热点数据读取对应文章，找不到则拒绝 |
| SEO 与分享信息仍指向旧站和旧功能 | `index.html` 的 `og:image`、`twitter:image` 指向 `aifringe.github.io`；description 写“本地 AI 问答”；缺少 canonical 和 `og:url` | 搜索结果和分享预览信息不准确，品牌和正式域名不统一 | 全部改为 `news.czrshe.com` 与“云端 AI”；增加 canonical、`og:url` 并验证分享图 |
| 项目说明严重过时 | README 仍写 GitHub Pages、本机 `127.0.0.1:8766`、Ollama `qwen3:8b` 和本地模型限制，与当前 DeepSeek、公共 API、宝塔正式域名不符 | 后续开发和排障会按错误架构操作，容易再次启用旧服务或错误部署 | 按当前架构重写使用、模型、更新、部署和验证说明，删除已废弃流程 |

## P2 一般

| 问题 | 出现位置与证据 | 影响 | 建议修改 |
| --- | --- | --- | --- |
| 代码质量门禁当前失败 | `pnpm lint` 报告 `app/page.tsx` 的 effect setState、memo 依赖、render 中访问 ref、无效 `href="#"`、未处理 Promise 和语义问题；还会扫描未跟踪的 `personal-site/` | 真实回归被大量错误淹没，无法把 lint 作为发布门禁 | 先限定 lint 范围排除 `personal-site/`，再逐项清理 `app/page.tsx`，将 lint 加入 Actions |
| 7 个原文链接返回非成功状态 | 135 个链接中 128 个为 200，5 个为 403，2 个为 429；包含 Economist 订阅内容、OpenAI 页面和 DeepSeek 新闻页 | “只收录可公开阅读全文”不能完全兑现，用户可能打不开或遇到订阅墙 | 更新时检测可读性；订阅墙降级为其他公开来源，403/429 标记为需复核而非直接判死链 |
| 缺少 robots 与 sitemap | 线上 `/robots.txt` 和 `/sitemap.xml` 均返回 404 | 搜索引擎抓取策略和正式页面发现能力不完整 | 新增两文件；若继续使用 hash 详情路由，sitemap 先收录主页并明确后续方案 |
| 静态页面缺少完整安全响应头 | 首页已有 HSTS，但未观察到 CSP/`frame-ancestors`、`X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy`；API 自身只有 nosniff 与 no-store | 增加点击劫持、第三方资源和引用信息暴露的防护缺口 | 在 Nginx 统一配置并逐项验证；CSP 先报告模式测试再收紧 |
| 限流计数存在并发和公共额度耗尽风险 | PHP 先读文件、再过滤、再写回；文件写入加锁但完整“读改写”不在同一把锁内。全站每日 300 次可被少量请求耗尽 | 并发时计数可能不准，恶意用户能让所有访客当天无法提问 | 用 Redis/数据库或持锁的原子读改写；增加成本监控、全局与单 IP 分层策略 |
| 缺少真实 Core Web Vitals 监控 | 生产构建 JS 421.73kB（gzip 132.97kB）、CSS 37.57kB（gzip 8.48kB）；当前没有 75 分位 LCP/INP/CLS 数据 | 无法判断真实网络和手机上的体验是否达到性能目标 | 接入 PageSpeed/CrUX 或轻量 RUM；依赖或界面大改后记录实验室数据与产物体积 |
| 移动分类栏可发现性较弱 | 320–430px 下分类项横向延伸到屏幕外，但页面本身不溢出；未见明确滚动提示 | 用户可能不知道右侧还有“安全与规则”“已收藏” | 增加轻微渐隐/末项露出或其他滚动提示，并保持键盘可达 |
