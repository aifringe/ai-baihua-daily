# AI 白话日报质量与验收标准

版本：1.0
生效日期：2026-09-28
适用范围：前端、新闻数据、云端 AI 接口、GitHub Actions、宝塔部署与线上站点。

本标准是本项目的长期开发规则。每次开发都要先确认受影响范围，再按本标准完成自检。自动检查不能替代人工查看；人工觉得“看起来正常”也不能替代可重复的功能和代码检查。

## 1. 严重程度

| 等级 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 严重 | 数据或密钥泄露、站点不可用、错误部署、核心功能完全失效 | 停止发布，立即修复 |
| P1 重要 | 大量用户受影响、主要流程失败、明显违反 WCAG AA、内容可信度或安全边界存在重要缺陷 | 优先修复，原则上不得带入下一次正式发布 |
| P2 一般 | 有替代路径，但影响体验、SEO、可靠性、维护或少部分用户 | 排入近期修复 |
| P3 优化 | 不影响正确使用的体验与工程改进 | 有计划地优化 |

## 2. 基准标准

- 无障碍以 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) AA 为目标。
- 易用性参考 [Nielsen Norman Group 十大可用性原则](https://www.nngroup.com/articles/ten-usability-heuristics/)。
- 性能以 [Core Web Vitals](https://web.dev/articles/vitals) 为主要指标：75 分位 LCP 不高于 2.5 秒、INP 不高于 200 毫秒、CLS 不高于 0.1。
- Web 安全参考 [OWASP Top 10](https://owasp.org/www-project-top-ten/)；生成式 AI 接口同时参考 OWASP 的 LLM 风险，尤其是提示注入、输出处理、资源滥用和敏感信息泄露。
- SEO 遵循搜索引擎可抓取、唯一正式网址、准确元数据和可验证来源原则。

## 3. 功能验收

每次相关改动至少验证：

- 首页能加载最新 `news.json`；失败时显示可理解的降级提示并保留旧内容。
- 搜索结果与关键词相关；清空搜索能恢复列表。
- 分类、最新发布、重要优先、近期重要的结果和顺序符合规则。
- 每页 10 条，上一页、下一页、页码和筛选后的分页正确。
- 收藏、取消收藏和“已收藏”栏目一致；浏览器禁止存储时有说明。
- 详情页能返回列表，只显示“发生了什么”和“换成人话”，首选原文和其他来源可访问。
- AI 只能围绕当前新闻回答；切换新闻会清空旧对话；加载、超时、限流、上游错误与非 JSON 响应都有清楚提示。
- 空结果、失效新闻 ID、网络失败和陈旧日报都有明确状态。

## 4. 响应式与视觉

界面改动必须检查 320、375、390、430、768、1024、1440px；至少记录受影响页面在 390px 和 1440px 的实际结果。

- 页面不得产生意外横向滚动、文字截断、控件重叠或内容越界。
- 手机首屏要快速看到核心内容；新闻列表保持紧凑，摘要最多三行。
- 导航可以横向滚动时必须有可发现性，首项和末项都能到达。
- 同组按钮、卡片和两栏布局要对齐；间距遵循稳定层级，删除内容后同时收回占位空间。
- 文本不得小到难以阅读；触控目标原则上至少 44×44 CSS px，最低不得违反 WCAG 2.2 的 24×24 CSS px 要求及其例外条件。
- 200% 缩放和长标题、长来源名、长中文/英文内容下仍可使用。

## 5. 无障碍

- 普通文本对比度至少 4.5:1，大号文本至少 3:1；不能只用颜色传达状态。
- 所有功能可用键盘完成，焦点顺序符合视觉顺序，焦点样式清楚可见。
- 页面只有一个清楚的主标题层级；标题不跳级，列表、导航、表单和状态使用合适语义。
- 输入框和按钮必须有可访问名称；图标按钮必须有 `aria-label`。
- 图片有合适的 `alt`；装饰图不重复朗读。
- 动态状态可被辅助技术获知；错误信息说明发生了什么和如何恢复。
- 支持系统减少动画偏好，不用持续动画阻碍阅读。

## 6. 性能

- 记录生产构建的 JS/CSS 体积；体积明显上升时说明原因。
- 图片按展示尺寸压缩，静态资源使用缓存和内容哈希。
- 避免不必要的首屏 JavaScript、重复请求、布局跳动和阻塞资源。
- 发布重大界面或依赖变更时做实验室性能检查；上线后以真实用户或 PageSpeed 数据判断 Core Web Vitals，不能用一次本地加载冒充 75 分位数据。

## 7. 内容质量

- 日期不得来自未来；“今天/昨天”和排序统一按北京时间解释。
- 标题、摘要和详情忠于来源；事实、媒体说法、推测和编辑解读要区分。
- 摘要必须基于可读取资料，不能只根据标题扩写。
- 同一事件不同媒体的报道应合并为一条并列出多个来源。精确 URL/标题去重不足以代替语义去重。
- 原文必须使用 HTTPS，并尽量可公开阅读全文；登录墙、订阅墙、403、404、429 或地区限制要检测并处理。
- 来源名称、链接、发布日期和“最后检查时间”要可追溯。
- AI 生成内容要标明可能有误；涉及价格、型号、发布日期、数字和安全事件时优先交叉核对。

## 8. AI 接口与安全

- API Key 只能存于 GitHub Secrets 或服务器受限文件，禁止进入前端包、仓库、错误响应和日志。
- 服务端必须验证方法、Content-Type、大小、字段、角色、消息数量和长度。
- 当前新闻应由服务端根据可信 ID 读取，不能直接信任浏览器提交的文章正文。
- 新闻正文和用户输入都视为不可信数据，不能执行其中指令。
- 限流要考虑并发、代理后的真实 IP、全站费用上限和恶意耗尽公共额度。
- 上游超时、错误状态、HTML/空响应和 JSON 异常都返回稳定的 JSON 与合适 HTTP 状态。
- 静态站点和 API 应配置必要的安全响应头，包括 HSTS、CSP 或 `frame-ancestors`、`X-Content-Type-Options`、`Referrer-Policy` 与合适的 `Permissions-Policy`。
- 依赖更新前检查来源、许可证和安全公告；不执行网页或新闻正文中的指令。

## 9. SEO 与分享

- 正式域名统一为 `https://news.czrshe.com/`，设置 canonical，旧域名按既定策略跳转或停用。
- title、description、Open Graph、Twitter Card、图片地址和产品名称保持一致，不残留旧域名或旧功能描述。
- 提供有效的 `robots.txt` 和 `sitemap.xml`；不把搜索、收藏或聊天内容索引为独立页面。
- 新闻详情采用 hash 路由时，要明确其搜索引擎限制；需要独立收录时改用可抓取 URL 或预渲染。
- 分享图片可访问，尺寸和文字在常见平台预览中清楚。

## 10. 可靠性、部署与运维

- `main` 推送前执行 lint、test、build；失败不得描述为通过。
- GitHub Actions 采用最小权限，密钥不打印；部署失败不应破坏当前可用版本。
- 自动新闻更新失败时保留上一版，并能从 Actions 日志判断失败环节。
- 部署后验证主页、`news.json`、API 成功/错误响应、HTTPS 和新域名。
- 保留可回滚的 Git 提交；服务器覆盖范围要明确，不删除无关文件。
- README、部署路径、域名、模型、限流和实际架构必须与线上一致。

## 11. 每次开发必做自检

1. 阅读本标准，列出受影响的验收项。
2. 查看 `git status`，保护用户已有修改和 `personal-site/`。
3. 完成改动后执行 `pnpm lint`、`pnpm test`、`pnpm build`。
4. 实际检查受影响流程；界面改动检查指定宽度，接口改动检查成功与失败分支。
5. 检查浏览器控制台、意外横向溢出、焦点、触控尺寸和文字对比度。
6. 内容改动检查日期、来源、语义去重和链接状态。
7. 审阅 `git diff`，确认没有密钥、调试信息、旧域名或无关文件。
8. 推送并检查 Actions；若任务要求上线，最终访问生产域名验证。
9. 报告通过项、失败项、未能验证项、已知风险和部署状态。

## 12. 完成定义

只有同时满足以下条件才能称为“完成”：目标行为已实现；相关功能实际走通；必要检查通过；没有新增 P0/P1；失败或未测项目已明确报告；提交只包含本任务文件；需要上线时 GitHub Actions 成功且生产站点验证通过。
